# Isolated Cloudflare BOOST staging deployment — operator runbook

**Status: NOT DEPLOYED.** This runbook must never deploy the production Worker `prime-lifting` or touch production Supabase `ctxhopadmvasxvjspwoi`.

## Hard isolation boundaries
- Git branch: `feature/prime-boost-staging` only.
- Preview Worker: `prime-boost-isolated-preview` from `wrangler.boost-preview.jsonc` only.
- Preview Supabase: `tarnzjkxexlozqqmyqof` only.
- Preview Worker static assets: `boost-preview-public/` generated by `npm run build:boost-preview`.
- **Do not run** `npm run deploy`, `wrangler deploy` without the explicit isolated config, or `git merge` into main.
- The original game's legacy `/api/login`, `/api/ranking`, `/api/daily`, `/api/achievements`, `/api/submit` endpoints are intentionally blocked on the isolated Worker. The staging game still contains legacy UI modules, so full game/leaderboard behavior is **not** release-ready.

## Local validation before enabling anything
1. On the staging branch: `npm ci && npm test && npm run check:boost-preview`. The last command builds assets and performs a **dry run**.
2. Confirm `wrangler.boost-preview.jsonc` names `prime-boost-isolated-preview`, pins `BOOST_PREVIEW_PROJECT_ID=tarnzjkxexlozqqmyqof`, and has `BOOST_PREVIEW_ENABLED=false`.
3. Confirm preview secrets are **unique and staging-only**; do not reuse the production Cloudflare, Supabase, JWT, or PIN secrets.
4. Prepare a dedicated test account UUID **in staging Supabase** and its inventory. Do not use a real player's production identity.

## Isolated preview deployment (requires operator's Cloudflare account)
Use a Cloudflare account that owns the isolated preview Worker and has permission to configure its secrets.

```sh
npm run build:boost-preview
npx wrangler deploy --config wrangler.boost-preview.jsonc
```

The first deployment intentionally keeps all preview API endpoints disabled by default. Verify static assets and the isolated hostname. Do not copy this config into the production Worker.

Configure the following **only on the isolated Worker** via Cloudflare's secret manager, not CLI arguments, repository, chat, or CI logs:
- `BOOST_PREVIEW_SESSION_SECRET`: unique 32+ character random secret
- `BOOST_RUN_SIGNING_SECRET`: different unique 32+ character random secret
- `BOOST_PREVIEW_SERVICE_KEY`: dedicated staging Supabase service credential

The worker also requires `BOOST_PREVIEW_LIMITER` and correct staging project binding. Verify the isolated Worker name in the dashboard before writing any secrets.

## Controlled test gate
1. Enable `BOOST_PREVIEW_ENABLED=true` on the **isolated** Worker only, leaving `BOOST_STAGING_RUNS_ENABLED` disabled.
2. Check `/boost-run-preview.html` inventory API using a signed preview tester token. Never enter production PINs.
3. After the inventory test, enable `BOOST_STAGING_RUNS_ENABLED=true` only on the isolated Worker, then test normal/TIME/SCORE/SC signed START/FINISH on a dedicated staging test account.
4. Create a tester token **locally** (never in GitHub Actions):
   `BOOST_PREVIEW_SESSION_SECRET=<private staging secret> node scripts/issue-boost-preview-token.mjs <staging-player-uuid>`
   It expires in 15 minutes. Treat its output as a password.
5. Open `/boost-game-preview.html` for a controlled PC/iPhone play only after the API smoke test succeeds. Do not claim replay compatibility or persistence until confirmed.
6. After testing, restore `BOOST_PREVIEW_ENABLED=false` and `BOOST_STAGING_RUNS_ENABLED=false` in the isolated Worker.

## Blockers before any real user-facing release
- The staging Worker is not deployed by GitHub Actions, and this environment has no connected Cloudflare deployment action.
- End-to-end browser gameplay has not been verified against the staging DB.
- The staging atomic RPC writes to a shadow leaderboard; daily challenges and achievements are not integrated.
- Confirm score replay, time boost duration, SC behavior, colored ball rendering, UI and reconnect on PC/iPhone.
- No production rollout without explicit approval and a separate migration plan.
